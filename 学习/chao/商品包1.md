

我去就先忽略掉一些业务背景，主要讲下系统的整体结构

**商品包是一个规则匹配系统。**

管理员会在后台配置规则，一个规则下会绑定大量 SKU。业务上游会根据 SKU 快速匹配命中的规则。

举个例子：

```json
{
    "ruleId": "rlue1",
    "skuIds":["sku1", "sku2", "sku3"]
}

{
    "ruleId": "rlue2",
    "skuIds":["sku2", "sku3", "sku4"]
}


"sku2" -> ["rule1", "rlue2"]
```



这个场景有两个特点：

* 数据量大
* 查询并发高

为了尽可能保证性能，我们主要在三个层面做了优化：存储、查询和写入



首先在存储层，我们会把每个规则按sku打散存储多条记录，以刚才说的规则1为例，一个规则下有三个3个sku，存到MySQL分库分表就是三条记录，按规则Id做分库分表，保证同一个规则的数据记录在同一个MySQL分片上，方便管理员管理和编辑。

但线上实际高频查询并不是 ruleId，而是：

sku → 查询命中的 ruleId

这会导致无法命中分片键。

所以我们的解决方案是额外设计了一张倒排索引表，把主表的数据同步一份到索引表，并按 sku 做分库分表，构建 sku 到 ruleId 的映射关系

本质上是通过空间换时间，解决MySQL分库分表后的多维度查询问题。



在查询层面，因为这个场景是典型的高频读、低频写，所以我们进一步把索引表全量同步到了 Redis。

查询时直接通过 sku 命中 Redis，完全绕过数据库，降低数据库的压力。

（T）缓存策略采用“逻辑不过期 + 主动更新”，尽量减少缓存失效带来的抖动问题。





在写入层面，因为一次导入可能涉及大量 SKU（10000个sku），如果同步写库，会导致事务过大和数据库写压力升高。

所以我们做了 MQ 异步分批处理。

导入时会按 400 个 SKU 拆成一个批次，每个批次发送一条 MQ 消息，由 Consumer 异步 消费到后再做小批量的insert。



（T）为了保证可靠性，我们还引入了类似“本地消息表”的设计。

（T）在发送 MQ 前，会先把批次状态落库；Consumer 消费成功后，再回写批次状态。

（T）如果中间出现 MQ 发送失败、消费失败或者系统异常，可以通过批次表进行补偿和重试，保证最终一致性。

总结下来，整个系统本质上是：

* 分库分表解决容量问题
* 倒排索引解决分库分表后多维度查询问题
* Redis缓存 解决高并发读问题
* MQ 引入异步分批处理，预防大批量可能引入的数据库压力过大的问题
